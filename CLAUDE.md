# CLAUDE.md

## Project Overview
Equity vesting tracker PWA. See SPEC.md for full requirements.

## Key Rules
- **NEVER commit real Epic share prices to this repo.** Epic share prices (purchase prices, annual market prices, or any per-share dollar values from Epic's internal communications or SharePoint) are confidential company financial data. They must never appear in source code, test fixtures, comments, or any committed file. All price fields must start blank — never hard-code or default any price values. The wizard may use prices the user has already typed in earlier steps (e.g. pre-filling cost basis from the prices table), but no real price values may be embedded in code.
- **backend/core.py is frozen.** Do not modify the core event generation logic. It is tested and verified. If you need to change event computation behavior, discuss first.
- **Events are never stored in the database.** They are computed on the fly from Grants + Loans + Prices via core.py.
- **backend/excel_io.py contains the Excel read/write logic.** Adapt as needed for the import/export endpoints but preserve the column mappings.
- **test_data/fixture.xlsx is a synthetic test fixture.** Use it to validate import logic. It contains no real data.
- **test_data/epic_share_summary.csv and test_data/epic_loan_statement.txt are synthetic fixtures** in Epic's own share-summary and Stock Loan Statement formats, used by `backend/tests/test_epic_import.py`. The prices and balances in them are invented round numbers — never replace them with real Epic figures.
- **backend/app/epic_import/ imports Epic's own files** (share summary CSV, Stock Loan Statement PDF). **The server never calls an LLM.** When a parse fails its checks, `prompt.py` builds a brief the user pastes into their own assistant; whatever comes back is validated by the same checks in `draft.py`. Vest dates, periods, exercise dates and loan rates come from the content tables via `skeleton.py` — an import fills figures into that skeleton and may not change it. Only C1/C2 (statement vs. its own printed totals) block; everything else is advisory. Acceptance goes through the wizard, never a file. Keep the rule ids (G*, L*, P*, S1, C1-C11) stable — they are how import bugs get reported. `backend/app/epic_import/RULES.md` explains every id and is pinned to the code by tests in `test_epic_import.py`: adding a rule without an entry there, or leaving the diagnostics legend in `reconcile.py` without one, fails the suite. `backend/tests/test_epic_import_drift.py` is the format-drift suite: each case pins that the drift is detected with the right codes, that a corrected draft converges against the same mutated files, and that the prompt carries what a repair needs. Add a case there whenever Epic's format changes.
- **Problem reports never carry financial data.** `POST /api/report` (`backend/scaffold/routers/reports.py`) is open to anyone, signed in or not. It stores the message, route, source, `error_ref` and the error text the UI already showed; account, user agent and the client trail are attached **only** when the reporter ticks "include details", which is off by default and leaves the report anonymous even on an authenticated session. Never add a field that carries share counts, prices, loan amounts or computed figures — import reports send rule ids (`C1`, `G3`, …), never finding text, because that text quotes the user's own figures. Reports live in `user_reports`, not `error_logs`, because the nightly job trims `error_logs` to 500 rows. `error_ref` is minted by the global exception handler in `main.py`, returned in the 500 body, and is how a report finds its traceback.
- **Schema migrations use Alembic.** Migrations live in `backend/alembic/versions/`. `alembic upgrade head` runs automatically in the lifespan on startup (PostgreSQL only; SQLite test environments use `create_all`). To create a new migration: `alembic revision --autogenerate -m "description"`.
- **Encryption is per-user.** When `KEY_ENCRYPTION_KEY` is set, `backend/scaffold/crypto.py` handles AES-256-GCM column-level encryption via SQLAlchemy TypeDecorators. Transparent to routers and core.py. Two-level hierarchy: KEK (env var, never changes) wraps the master key stored encrypted in `system_settings`; master key wraps per-user keys. `initialize_master_key()` is called from lifespan; `reload_master_key_if_stale()` is called from `EncryptionMiddleware` to auto-propagate rotations to all replicas within 5 seconds.
- **Encryption fails closed, and the key is set in the middleware.** With encryption configured, a write with no key in context raises `EncryptionKeyMissing` rather than storing plaintext, and reading a `$ENC$` value with no key raises rather than returning `0.0`/`0`/`None`. Plaintext rows (no `$ENC$` prefix) still read through, so pre-encryption databases keep working. The key **must** be set in `EncryptionMiddleware`, in the ASGI context: FastAPI runs sync dependencies in a threadpool that gets a *copy* of the context, so a key set inside `get_current_user` never reaches the endpoint. The middleware reads the session cookie *and* the `Authorization: Bearer` header — native shells send only the latter. Anything running outside a request (the daily notification job, `event_cache._do_recompute`) must set the key itself per user and clear it afterwards. In tests, seed rows through the `user_key` context manager in `conftest.py`.
- **One deletion service.** `backend/scaffold/user_deletion.py` is the only place that erases a user; both `DELETE /api/me` and the admin endpoint call it. `USER_OWNED_TABLES` is the contract and a test in `test_user_deletion.py` walks the ORM metadata against it — a new table with a `user_id` column fails the suite until it is either deleted or deliberately de-linked.
- **Invitation secrets never sit in the database.** `invitations.token` and `.short_code` hold HMAC verifiers (`backend/scaffold/invite_tokens.py`), not the secrets. The raw token exists only long enough to build the email link, so **resend mints a fresh token** and the old link dies. The short code additionally has a sealed copy in `short_code_sealed` because the sent-invitations list displays it. Accepting deliberately does *not* require the account email to match `invitee_email` — the invitation email promises exactly that, and `invitee_account_email` records the mismatch.
- **An MCP tool calls the same service function the HTTP endpoint calls.** `backend/app/mcp/read_tools.py` goes through the `_get_dashboard_data(user, db)` / `_get_events_data(user, db)` helpers in `app/routers/`, which already take an arbitrary user because sharing needed that first. A tool must never re-derive a figure: an assistant and the web app disagreeing about someone's vesting schedule is worse than either being wrong alone, and `test_mcp_tools.py` asserts the two answers match rather than hardcoding expected numbers. Every tool also takes `account` and resolves it through `app/mcp/accounts.py:resolve_account` — today it accepts only `"me"`, and extending it to shared accounts means delegating to `sharing.py:_get_shared_owner`, which already does the encrypted-key swap correctly. Tool arguments come from a language model, so bad input raises `ValueError` and becomes a tool error; an unhandled exception would be a 500 and an `error_logs` row.
- **Every MCP read is audited, and the entry is written before the tool runs.** `scaffold/oauth/audit.py` inserts the `mcp_audit` row first and updates its outcome afterwards, so a failed audit write refuses the call rather than serving data off the books — `oauth_grants.last_used_at` alone was one timestamp overwritten per request, which says a connection was used, not what it read. **The table carries no financial data**: tool names, scopes and outcomes only, never arguments, figures or results — the same rule as `user_reports`, and `test_mcp_audit.py` walks the columns to keep it. `grant_id` deliberately has no foreign key, because the record of what a connection did must outlive disconnecting it. `/mcp` is rate limited per connection *and* per account in `app/mcp/transport.py`: nothing else covers that path (the mutation limiter only inspects `/api/`, and an IP-keyed limit would count the provider's servers, not the user's). The nightly job in `scaffold/oauth/cleanup.py` prunes unused client registrations, abandoned authorization codes and old audit rows — all three grow on their own, and anonymous dynamic registration means a stranger can add to the first.
- **A connector can prepare an import but never apply one.** `app/mcp/import_tools.py:stage_import` runs a draft through the same two passes an uploaded file gets — `draft_from_payload` then `validate_draft`, with no statement, so the C1/C2 file-reconciliation checks drop out and the structural rules stand — and writes an `import_proposals` row. It writes no grant, price or loan: `epic_import/` requires that acceptance goes through the wizard and never a file, and that holds however the draft was produced. The wizard prefill is derived when the app reads the proposal, never stored, because `_wizard_prefill` folds in the prices the account holds *now* and the wizard deletes rows its payload omits — a frozen prefill would silently drop whatever the user added since. The `import:propose` scope is not in `DEFAULT_SCOPES`: nothing that leaves a trace arrives without being asked for, and the consent screen stops saying "read-only" whenever a scope in `WRITING_SCOPES` is granted.
- **A connector token is not a session token.** `backend/scaffold/auth.py` mints two kinds of JWT and the type claim decides where each works: `get_current_user` refuses anything that is not `typ: "session"`, and `scaffold/oauth/resource.py:require_connector` refuses anything that is not `typ: "mcp"`. Tokens predating the claim carry no `typ` and read as session, so nobody was signed out by the split. Without both halves a leaked AI-connector token would be a full account session, `/api/admin/*` included — `test_oauth_server.py` pins both directions. Connector tokens are also bound to this server by `aud` (RFC 8707) and checked against their `oauth_grants` row on every request, which is what makes Disconnect immediate rather than "at the next expiry". Never widen `decode_jwt` into an authorization decision: it verifies signature and expiry only, deliberately, because `EncryptionMiddleware` needs the subject of *either* kind to put the right data key in context.
- **The OAuth server's redirect validation is its own, and `E2E_TEST` must never reach it.** `scaffold/oauth/clients.py:validate_redirect_uri` is separate from `auth_router._validate_redirect_uri` on purpose — the login flow's copy is skipped under `E2E_TEST=1`, and an authorization server that inherited that would hand authorization codes to any address a caller named. Dynamic client registration is anonymous, so the admin-managed provider allowlist (`oauth_redirect_hosts`, read through `scaffold/oauth/settings.py`) plus exact (never prefix) redirect matching plus consent shown every time are what close the confused-deputy hole. Whether connections are on at all, and which providers are allowed, are DB settings and **not** environment variables — a test greps `app/` and `scaffold/` to keep it that way, because a stale env var silently overriding the admin page is the failure this move was meant to remove.
- **User-supplied URLs the server fetches must be validated.** Push endpoints go through `backend/scaffold/push_endpoints.py` at subscribe time *and* again in `send_push`, because DNS moves and subscriptions are long-lived. Any new feature that makes the backend fetch a caller-supplied URL needs the same treatment.
- **Uploaded archives are measured before they are parsed.** An `.xlsx` is a zip, so the 5 MB upload cap bounds the wire, not the memory: deflate reaches ~1000:1 and `openpyxl.load_workbook` builds the whole thing before the endpoint sees a cell (`read_only=True` still loads `sharedStrings.xml` whole). Every endpoint that opens a caller-supplied workbook calls `load_workbook_safely` / `check_workbook_bytes` from `backend/scaffold/safe_workbook.py` — never `openpyxl.load_workbook` directly. A new upload endpoint does the same.
- **A malformed upload is a finding, never an exception.** The parsers in `backend/app/epic_import/` are reachable without a session through `POST /api/trial/analyze`, and every unhandled exception becomes a 500 that writes an `error_logs` row — which the nightly job then uses to trim real tracebacks out of the 500-row window. So a bad figure, an impossible date, an oversized CSV field or an out-of-range year returns a `Finding`; grant years are bounded by `MIN_GRANT_YEAR`/`MAX_GRANT_YEAR` in `draft.py` because every schedule below them is `date` arithmetic. `draft_from_payload` takes text an assistant produced and must not raise on any shape.
- **A PDF's cost is bounded by its text, not its page count, and measured before it is parsed.** Characters cost ~2 KB of memory each in pdfminer, so 64 dense pages in a 36 KB upload cost ~980 MB and one crafted page can exhaust the 512 MB container — a page limit does not touch either. `_measure` in `pdf_statement.py` counts show-operator bytes off the decompressed content streams and refuses anything past `MAX_TEXT_CHARS` (a real statement is 1.4k characters, a 200-row one 13.6k). `PDF_PARSE_SLOTS` caps concurrent parses and sheds load with 503 rather than queueing. Never move these bounds without re-measuring; `test_upload_hardening.py` builds the adversarial PDFs.
- **`E2E_TEST=1` is a development-only switch and the app refuses to boot with it alongside `DOMAIN` or `APP_ENV=production`** (`backend/scaffold/auth.py`). It disables every rate limit, redirect_uri validation and the push SSRF checks, accepts a default `JWT_SECRET`, and registers `/api/auth/test-login`, which mints a session for any address asked for.
- **Exported cells are text unless the server authored the formula.** In `backend/app/excel_io.py`, `w()` escapes any value starting with `=`, `+`, `-`, `@`, tab or CR; server formulas go through `wf()`. `_safe_str` in `import_export.py` does the same for the other workbooks. Never widen the exclusion list to let user data through — a grant type reaches another person's spreadsheet through the shared-account export.
- **Cache invalidation is coalesced.** `schedule_recompute`/`schedule_fan_out` in `backend/app/event_cache.py` queue work for one dispatcher and a fixed pool (`EVENT_CACHE_WORKERS`); never spawn a thread per invalidation. Rows owned by one user (prices included) recompute that user only — `schedule_fan_out` is for the internal invalidation webhook.
- **User-writable fields are bounded.** New free-text fields get a length in `backend/schemas.py` (`MAX_LABEL_LEN`, `MAX_NOTES_LEN`), new list bodies get an item cap (`MAX_BULK_ITEMS`), and a new user-owned table gets a row ceiling in `backend/scaffold/quota.py`. `MUTATION_RATE_LIMIT` (middleware in `main.py`) caps writes per account per minute on top of that.
- **Never key a rate limit on `request.client.host`.** Behind Caddy that is the proxy's address for every caller, collapsing the limit into one shared bucket. Use `client_ip()` from `backend/scaffold/client_ip.py`. It prefers `CLIENT_IP_HEADER` (set to `CF-Connecting-IP` behind Cloudflare — one address, no counting, and only trustworthy because the origin is firewalled to Cloudflare's ranges) and otherwise unwraps `X-Forwarded-For` as far as `TRUSTED_PROXY_HOPS` allows. That hop count fails silently in the worst direction: Cloudflare in front with the default of `1` resolves every caller to a Cloudflare edge address. `GET /api/admin/client-ip` reports what was actually resolved — check a deployment rather than assuming it.
- **Anonymous budgets are sized for a shared office network.** Everyone at one company leaves through a handful of addresses (IPv4 NAT, and the IPv6 /64 grouping below), so every IP-keyed limit is shared by all of them — `/api/auth/callback` at 20 per 15 minutes meant the 21st colleague to sign in could not. Keep them generous enough for an office; `test_anonymous_budgets_leave_room_for_one_office` pins a floor. Real resource protection belongs in hard bounds (`PDF_PARSE_SLOTS`, `MAX_TEXT_CHARS`, the body limit), not in these. A 429 must name the network and carry `Retry-After`, never tell a blameless caller to slow down.
- **Anonymous endpoints use `check_rate_ip_shared`, never `check_rate_ip`.** They have no user id to count against, and the per-process counter is multiplied by worker count and reset by every deploy. The shared one counts in Redis (falling back to per-process when Redis is down). Both bucket the address through `_ip_bucket` first: an IPv6 caller owns a whole /64, so counting per address was no limit at all — 50 requests from one /64 passed a limit of 5.
- **Admin access is dynamic.** Set via `ADMIN_EMAIL` env var (semicolon-delimited). `is_admin` flag is set on every login — no persistent admin designation. Admin endpoints in `backend/scaffold/routers/admin.py` never expose financial data.
- **OIDC_PROVIDERS format:** JSON array of provider objects. Required fields: `name`, `label`, `client_id`, `discovery_url`. Optional: `client_secret` (omit for PKCE-only clients), `scopes` (default `["openid","email","profile"]`), `subject_claim` (default `"sub"`; use `"oid"` for Azure Entra ID), `prompt` (default `"select_account"` — keeps the IdP account chooser from being skipped; `""` omits it). Multiple providers show as separate login buttons. Redirect URI to register in IdP: `https://yourdomain.com/auth/callback`.

## Deployment Rules
- **Never fix production by running commands manually on the server.** Manual fixes get overridden by the next deploy and leave the repo out of sync with reality. Every fix must go through code → PR → merge → deploy.
- **The deploy script is the source of truth.** If something needs to happen on the server, it must be in `.github/workflows/deploy.yml`. If you find yourself saying "just run X on the server," stop and put X in the deploy script instead.

## Build Order
Follow the order in SPEC.md. Build backend first, then frontend. **Every step must include tests before moving on.** Ask before making architectural decisions.

## Testing Rules
- **No feature without tests.** Write tests alongside or before the implementation, not after.
- Backend: pytest. Use test_data/fixture.xlsx as a fixture for import/export tests.
- Frontend: Vitest + React Testing Library.
- E2E: Playwright, mobile viewport (375x812), chromium only.
- **Always run `npx tsc -b --noEmit` before committing frontend changes.** The dev server skips type-checking; CI catches it.
- **Run E2E tests via `./e2e.sh` from the repo root.** This script handles type-checking, starting a fresh backend + Vite server, waiting for both to be healthy, and cleanup. Do not manually spin up servers and run Playwright separately.
- Known-good values for core logic validation: 89 events, final cum_shares=558500, cum_income=$144,325, cum_cap_gains=$1,224,195. (cum_shares was 269843 before Loan Payoff refactor; was 571500 before fixture dp_shares updated from -2000 to -15000.)

## Debugging CI Failures
- **Read CI logs with `curl`, not WebFetch.** WebFetch truncates large log files mid-build and never reaches the test output. Use:
  ```bash
  curl -s "<log-url>" | tail -c 30000
  ```
  The test failures appear at the end of the log (after the Docker build). `tail -c 30000` reliably skips the build noise and lands in the Playwright output.
- **Backend errors from E2E runs:** When Playwright tests fail, the CI workflow runs `docker compose logs e2e-app` automatically (the "Dump backend logs on failure" step). Look for that step in the GitHub Actions run — it contains full Python tracebacks including the SQL, parameters, and exception type. Do not put exception details in HTTP response bodies; keep them in server logs.
- **`loginAs` failures:** If `POST /api/auth/test-login` returns non-2xx, check the backend logs first. Common causes: `DatatypeMismatch` (passing Python bool to an INTEGER column — always use `int(...)`), `IntegrityError` from a concurrent insert race (handled by the retry loop in `test_login`), or a missing `E2E_TEST=1` env var (endpoint not registered).

## README Documentation Checklist
> **⚠️ MANDATORY: Update README.md whenever any of the following change. DO NOT ship a feature without updating the docs.**

- **User-facing features** — new pages, workflows, or settings a user would interact with: update the "How to use" / getting started section of the README.
- **Admin workflows** — new env vars, admin endpoints, operational procedures (e.g. notifications, user management, blocked users): update the admin/ops section of the README.
- **Code structure** — new routers, models, services, frontend pages, or hooks added: update the architecture/code structure section of the README.
- **Environment variables** — any new `SOME_VAR` required or optional: document it in the README env var table.
- **Auth provider config** — any change to OIDC provider support, PKCE flow, callback URI, or how `OIDC_PROVIDERS` is parsed: update the OIDC_PROVIDERS format section in README and FORK_GUIDE.md.
- **Deployment architecture** — any change to docker-compose topology, Caddy config, proxy network, or GitHub Actions secrets/vars: update the Production Deployment section in README and the GitHub Actions secrets table in OPERATIONS.md.
- **What to update in README.md:**
  1. Feature description / how to use it (user perspective)
  2. Admin/ops notes if it affects deployment or server config
  3. Code structure diagram or file list if new files were added
  4. Any new env vars with description and whether they are required
